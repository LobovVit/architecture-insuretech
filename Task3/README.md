# Task3 — Переход на Event‑Driven архитектуру: проблемы и риски (as‑is → рост нагрузки)

## Контекст (as‑is)
- `core-app` и `ins-comp-settlement` получают продукты/тарифы через REST API `ins-product-aggregator`.
- `ins-product-aggregator` в рамках **одного синхронного запроса** опрашивает **все** страховые компании, агрегирует и возвращает ответ.
- `core-app` обновляет локальную реплику раз в 15 минут, `ins-comp-settlement` — раз в сутки.
- `ins-comp-settlement` раз в сутки запрашивает в `core-app` список оформленных страховок за день.
- Планируется рост числа страховых компаний: **5 → 10**.

## 1) Проблемы производительности и доступности
1. **N+M fan‑out в синхронном запросе**  
   Каждый REST вызов к `ins-product-aggregator` порождает до N внешних вызовов (сейчас 5, будет 10). Латентность = max/сумма внешних латентностей + накладные расходы, повышается вероятность таймаутов и частичных отказов.
2. **Каскадные таймауты и "цепная" деградация**  
   Любая деградация API страховой компании транслируется в деградацию `ins-product-aggregator`, затем в `core-app`/`ins-comp-settlement` → рост ретраев → лавинообразная нагрузка.
3. **Отсутствие backpressure и управление всплесками**  
   При росте нагрузки (и числа компаний) `ins-product-aggregator` становится бутылочным горлышком. Синхронный REST не даёт естественной буферизации.
4. **Ночная пакетная нагрузка**  
   `ins-comp-settlement` раз в сутки выполняет тяжёлую операцию: (а) обновление продуктов и (б) выгрузка страховок из `core-app`. На росте объёмов — риск длительных окон, выход за SLA и конфликт с ночными окнами/бэкапами.
5. **Single point of pain**  
   Падение/деградация `ins-product-aggregator` блокирует обновление реплик и потенциально бизнес‑операции, зависящие от актуальных тарифов.

## 2) Проблемы консистентности данных
1. **Сильная рассинхронизация локальных реплик**  
   `core-app` обновляется каждые 15 мин, `ins-comp-settlement` — раз в сутки → сервисы работают на разных версиях каталога, возможны разные расчёты/отчёты.
2. **"Окна несогласованности" при сбоях**  
   Если обновление по REST упало/зависло, реплика не обновится до следующего запуска. Нет гарантированного механизма доставки.
3. **Нет трассируемости версии каталога**  
   Сложно ответить “по какой версии продукта/тарифа оформлялась страховка” и воспроизвести расчёт.

## 3) Риски роста до 10 страховых компаний
1. **Рост внешних соединений/ресурсов**  
   Больше TLS‑handshake/соединений, потребление потоков/памяти, выше вероятность исчерпания пулов.
2. **Усложнение ретраев/лимитов/квот на внешние API**  
   Ошибки партнёров начнут “дробить” SLA внутренней системы.
3. **Увеличение MTTR из‑за слабой наблюдаемости**  
   При цепных деградациях становится сложнее понять первопричину: какой партнёр и какая операция виноваты.

## 4) Риски интеграции между `ins-comp-settlement` и `core-app`
1. **Пакетная выгрузка оформленных страховок по REST**  
   Рост объёма приведёт к длинным ответам, большим payload, проблемам памяти/таймаутам, повторным запросам (дубликаты).
2. **Сложность повторного запуска**  
   Если джоб упал в середине — нужен сложный механизм "дозагрузки" и дедупликации.
3. **Сильная связанность (temporal coupling)**  
   `ins-comp-settlement` зависит от доступности `core-app` именно в момент ночного окна.

## 5) Ключевые последствия без изменений
- Увеличение количества инцидентов из‑за таймаутов и деградации внешних API.
- Снижение актуальности данных о продуктах/тарифах и расхождение расчётов.
- Рост стоимости инфраструктуры (ретраи, пики, перерасход ресурсов).
- Сложная эксплуатация и долгое расследование инцидентов.

# Предлагаемое решение (to‑be, без изменения декомпозиции сервисов)
## Что переводим на Event‑Streaming
1. **Каталог продуктов/тарифов**  
   `ins-product-aggregator` публикует события:
   - `product_catalog.snapshot` (полная версия/снимок, реже)
   - `product_catalog.changed` (инкрементальные изменения, чаще)  
   `core-app` и `ins-comp-settlement` подписываются и обновляют свои локальные реплики.
2. **Оформленные страховки**  
   `core-app` публикует события домена:
   - `policy.issued` / `insurance.purchased` (и при необходимости `policy.cancelled`, `policy.updated`)  
   `ins-comp-settlement` подписывается и формирует дневные/месячные реестры **из событий**, без ночного REST‑опроса.

## Transactional Outbox — использовать
Да. Для:
- `core-app` (надёжная публикация `policy.*` вместе с записью в свою БД)
- `ins-product-aggregator` (надёжная публикация `product_catalog.*` вместе с записью/версией каталога в своей БД/хранилище)
Паттерн: таблица outbox + воркер/дебезий‑подобный publisher, гарантии **at‑least‑once**, на стороне консьюмера — **идемпотентность** (dedupe по `event_id`).

## Дополнительно (важно для эксплуатации)
- DLQ/Retry topics для "ядовитых" событий.
- Schema Registry (Avro/Protobuf/JSON Schema) + версионирование событий.
- Корреляция/трейсинг: `trace_id`, `correlation_id`, `catalog_version`.
- Consumer groups и горизонтальное масштабирование потребителей.
- Мониторинг: lag по топикам, процент ошибок обработчиков, DLQ, latency end‑to‑end.
